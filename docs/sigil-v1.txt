SIGIL PROTOCOL SPECIFICATION
Version 2/3 · writers emit v2 (plain) and v3 (encrypted, private label) · readers accept v1–v3 · AGPL-3.0 (programs) · Apache-2.0 (this layout)

New Sigils are version 2: first k shards are the payload (systematic Reed–Solomon);
parity shards are extra evaluations. Version 1 evaluation-code files still De-scribe.
Default mode is Reflection (~1.3×, ~25% shard loss). Seal is opt-in (~2×, ~50%
shard loss). Loss means whole shards; see THREAT MODEL for scattered bit rot.

Sigil is a portable object format (.sg1); one .sg1 file is called a Sigil.
The format combines a content identifier,
Reed–Solomon erasure coding, replicated headers, and optional AES-256-GCM.
It is not a network, filesystem, identity provider, or replacement for PGP,
rsync, IPFS, or a database. Independent implementations must match this layout.

OBJECT
A .sg1 packs a payload into n shards (default 16; the CLI may increase n).
  true name  SHA-256 of the original plaintext
  binding    Merkle root of shard hashes
  Ward       optional AES-256-GCM. New passphrase seals: random content key
             wrapped with Argon2id (parameters stored, SGTO v2). Legacy Wards:
             key = PBKDF2-HMAC-SHA256, 80 000 iterations (read-only)
  Keystone   three extra copies of the 160-byte header after the primary
  Ember      SGEM-tagged header copy at the start of each shard
  Covenant   optional purpose string (not an access-control decision)
  Geas       optional companion SHA-256 values; decode refuses if absent
The fold (logistic permutation from a random salt) is obfuscation, not a cipher.
Confidentiality is claimed only when a Ward is present.

MODES (repair ratio is fixed; n may scale)
Glyph        k = n           identity / stripe; no repair
Reflection   k = 3n/4        ~25% shard loss; stored size ~1.3×
Seal         k = n/2         ~50% shard loss; stored size ~2×
If fewer than k shards are live, decode refuses. It does not guess plaintext.

SHARD DISTRIBUTION (CLI)
Scatter      export the n canonical shards as .sgp files
Deluge       extra evaluations of the same polynomial (indices n…254)
Gather       rebuild a canonical .sg1 from any k distinct shards
Vessel       marker file written when Gather has enough shards
Coven        rsync gossip: peers exchange .sgp files; first peer able to
             reconstruct mints new Deluge indices for the rest
Glyph cannot Deluge. Distinct --from lanes avoid duplicate indices among peers.
Maximum distinct index is 254 (GF(256)).

ACCESS
The only secret in v1 is the Ward. A label in the object is not authorization.
RBAC / ABAC / PBAC require a live policy service. A .sg1 does not know a subject.

STAR / CONSTELLATION
A star is one .sg1. A constellation is a named list of stars.
The same star may appear on more than one list.
On disk: a folder of loose stars plus a card (a Seal whose payload is SIGG).
An atlas (.sga, ATLS) is the card plus the member stars in one bag.
De-scribe of a constellation refuses if a named star is absent.

VERIFYING A COPY WITHOUT SIGIL
SHA-256 the entire .sg1 (envelope hash) at source and destination.
Reconstruction requires an implementation:
  sigil scry file.sg1
  sigil de-scribe -o out.bin file.sg1

HEADER (160 bytes)
0-3     SGIL
4       version = 1, 2, or 3 (3 = private label, encrypted only)
5       flags: deflate | Ward | mode | constellation | Keystone | Ember | Vow
6-7     k, n
8-15    original length (u64 le; 0 on v3)
16-23   folded length (u64 le)
24-55   true name (v3: keyed fingerprint)
56-71   salt
72-83   AES-GCM nonce
84-99   AES-GCM tag
100-103 shard length (u32 le)
104-107 entropy milli-bits; Ember may store piece index in the high byte
108-111 header CRC32 (this field zeroed)
112-127 original file name (UTF-8, padded; empty on v3)
128-159 binding
160-639 Keystone (three copies)
640-767 Vow slab if FLAG_VOW
then    n × (Ember SGEM 160 [+ Vow] + shard + CRC32 of shard)

Ember magic is SGEM so a shard prefix is not mistaken for the object front.
Shard CRC covers payload only, so the binding is independent of Ember bytes.
The Vow is copied after each Ember so Geas still applies if the prefix is gone.

Work packs (magic SGWK) concatenate sequential .sg1 stars for large payloads.
The browser lab remains size-capped; the Rust CLI is not.

DERIVED CARRIERS (no change to the .sg1 layout)
Both carriers below are built from an existing .sg1 and rebuild a
.sg1 of the same object, checked against its hash before output.
Neither adds confidentiality or authenticity:
a Ward, if any, stays inside the .sg1, and the carriers need no key.

Channel (sigil deluge --channel; old hidden alias --fountain)
  Encodes the whole .sg1 with RaptorQ (IETF RFC 6330) into rateless
  packets called mana, one per file, extension .mana only.
  Packet file v2: "SGFT" | 2 | OTI (12) | object SHA-256 (32) |
    FEC payload id (4: 8-bit source block number, 24-bit ESI) |
    symbol | SHA-256 of all preceding bytes (32).
  v1 packets ("SGFT" | 1 | OTI | payload id | symbol) are still read.
  Default ESIs are random over the 24-bit space, so uncoordinated
  senders rarely duplicate a packet and their packets can be pooled.
  Gather drops damaged, truncated, foreign or impossible packets and
  duplicate ESIs, and writes output only if the rebuilt bytes match
  the object SHA-256. The trailing SHA-256 is an integrity check, not
  a MAC: anyone can forge a packet with a valid checksum; such a packet
  is caught only by the final object hash, so gather fails closed
  (no wrong output) but an attacker who can inject packets can deny
  recovery. RaptorQ decoding is probabilistic: K source symbols
  usually suffice, sometimes 1-2 more are needed (RFC 6330 5.8).
  Details: docs/FOUNTAIN-v2.md.

Frost Rune (sigil frost place / frost mend; alias frost-rune;
  deprecated hidden aliases kit, cold-usb)
  Placement only, no new code: the n shards of one Seal .sg1, as
  scatter pieces (.sgp), are dealt round-robin into folders
  usb-0 .. usb-(D-1) (default D = 4, so 4 of 16 shards per drive), plus a plain-text manifest named KIT
  listing star_id (true-name hex), n, k and shard=i usb=j rows.
  Losing whole drives is tolerated while at least k shards survive
  (Seal 8 of 16: any two of four default drives). frost mend gathers
  the pieces in the folders that remain, with the same checks as
  sigil gather. The manifest is not authenticated; the rebuilt Sigil is
  still checked against its true name and length.
  Details: docs/LRC-COLD-USB.md.

Fire Rune is a reserved name for a future hot-storage counterpart.
It has no behavior and nothing about it is claimed here.

THREAT MODEL
This section states what a .sg1 protects, against whom, and what it does not.
It describes the reference implementation (crate/sigil) as of October 2026.

Assets
  payload      the original bytes: their confidentiality (only when a Ward
               or encrypt-to wrap is present) and their recoverability
  identity     the true name (SHA-256 of the plaintext) and the binding
  metadata     file name, sizes, entropy score, mode and shard geometry
  secrets      the Ward passphrase and .sgk identity keys (kept outside
               the .sg1; only wraps of a random content key are inside)

Adversaries
  F  faults: bit rot, torn or truncated writes, lost pieces, a smashed
     front of file. Not malicious.
  P  passive holder of a copy without the key (cloud host, courier,
     finder of a lost USB stick). Reads every byte, changes nothing.
  A  active tamperer without the key: edits bytes, swaps whole Sigils,
     crafts hostile headers, piece files, packs and SGTO blocks.
  G  offline guesser: runs the passphrase KDF on candidate passphrases.
  K  anyone holding the passphrase or identity key: full access, by
     definition out of scope.

In scope (what is claimed)
  F  Exact recovery while at least k shards are intact; otherwise decode
     refuses and names the shortfall. It never returns different bytes:
     the output must match the true name and length.
     Repair is SHARD ERASURE. A shard whose CRC32 fails is dropped whole,
     so one flipped bit costs a whole shard. Up to n-k damaged shards are
     tolerated however the damage is spread (Reflection 4 of 16, Seal 8
     of 16 at the default n). For unseal and plain mend, bit flips
     scattered across more than n-k shards are NOT recoverable, even at
     very low rates. `sigil mend --soft` (reference implementation, no
     layout change) also decodes each byte column on its own and fixes up
     to (present-k)/2 wrong symbols per column, accepting the result only
     if the Merkle binding and true name match; measured numbers are in
     docs/research/DEEP-SPACE.md. Keystone and Ember copies keep the
     header findable when the front of the file is destroyed.
  P  With a Ward or encrypt-to wrap, payload content is protected by
     AES-256-GCM under a 256-bit key. The fold is not a cipher.
  A  On encrypted Sigils the GCM tag rejects any change to the payload.
     On every Sigil the decoder checks the true name and length after
     decode. Parsers treat all input as hostile: malformed geometry,
     counts and lengths are errors, not panics or unbounded allocations.
     NOT claimed: authenticity of an unencrypted Sigil. The header is
     protected only by CRC32, so whoever rewrites payload and header
     consistently produces a valid Sigil with a new true name. Proving
     origin needs a signature kept outside the header (sigil sign,
     an Ed25519 attestation) or a true name learned out of band.
  G  Cost per guess is the KDF. New passphrase wraps (SGTO v2, record
     kind 3) use Argon2id with stored parameters, defaulting to
     m = 19456 KiB, t = 2, p = 1 (the OWASP Password Storage Cheat Sheet
     minimum); readers cap stored parameters before deriving. Legacy
     Wards and SGTO v1 passphrase wraps use PBKDF2-HMAC-SHA256 at a fixed
     80 000 iterations (below OWASP's 600 000 for that hash). They stay
     readable and are as weak as they always were. Re-seal them to
     upgrade. No KDF saves a guessable passphrase.

Out of scope (what is not claimed)
  Metadata confidentiality. FIXED FOR NEW ENCRYPTED FILES (header v3,
    "private label", October 2026; options 1 and 4 on by default). Every
    new encrypted Sigil (passphrase, encrypt-to, both, Talisman; single
    seals, work-pack stars, constellation stars, log segments) writes:
      - outside: magic, version 3, flags (deflate bit cleared), k, n, the
        CIPHERTEXT length, salt, nonce, tag, shard length, the Merkle
        binding, and a KEYED FINGERPRINT in the true-name slot. Name,
        original length and entropy slots are zero.
      - inside the AES-256-GCM plaintext, before the body: an SGIN block
        with the real name, original length, folded length, plaintext
        SHA-256, entropy score, deflate flag and (pack star 0) the pack
        total. Readers check the inner SHA-256 and length after decrypt.
      - the 160-byte label as GCM associated data ("sigil v3 label\0" ||
        label, with the CRC, tag, shard length, Ember index/entropy and
        binding bytes zeroed). Those excluded bytes are bound separately:
        the binding is recomputed from the shards and must match, the
        entropy slot must be zero. Editing any label field, swapping
        labels or fields between Sigils, or rewriting v3 to v2 fails closed.
      - keyed fingerprint = HMAC-SHA256 (RFC 2104) of the plaintext under
        HKDF-SHA256 (RFC 5869): ikm = content key, salt = file salt,
        info "sigil v3 keyed fingerprint". Per file by default, so two
        seals of the same file do not match. An opt-in shared dedupe key
        (library SealOpts) makes equal files match for its holder only.
    Work packs with an encrypted payload write an empty name and a zero
    total in the pack front and guards; facets list the stars' keyed
    fingerprints, not chunk hashes. Constellation stars are filed under
    a ciphertext id (Merkle binding; for a pack, SHA-256 of its facet
    list). Mend, scry, doctor and log verify need no key: they check
    shard CRCs and the Merkle binding of the ciphertext. Name and size are
    shown only after unlock (scry prints "label=private" / "(locked)").
    Cost: about 72 bytes plus the name length inside the ciphertext,
    times the parity ratio, rounded up to whole shard rows (measured: a
    10 000-byte file grows from 3 461 to 3 573 bytes; under 0.01% for
    MiB-sized files). Plain Sigils and every existing .sg1 are unchanged
    and open exactly as before.
  STILL LEAKS (not fixed, or fixed only by opt-in):
      - every v1/v2 encrypted Sigil written before the fix: re-seal it.
      - the ciphertext length, i.e. the compressed size plus ~72 bytes plus
        the name, unless the seal was made with opt-in `--pad bucket`
        (size buckets, ≤ ~6.25% growth) or `--pad max` / `pow2` (next
        power of two). Default remains off (no silent size growth).
        `--pad` needs encryption and is single-file for now.
      - folder packs (SGDR) written before sealed directories, or protected
        only by per-file wards: member names and sizes inside the folder
        record, and per-member plaintext SHA-256 for large members. An
        encrypted pack is now written as SGDR ver=2 ("SGDR" | 2 | count u32
        | body_len u64 | body), where body is one encrypted Sigil or work pack
        whose plaintext is the ver=1 pack; only the file count and the total
        ciphertext length stay visible (docs/PRIVATE-LABEL.md).
      - vault CHART version lines: plaintext SHA-256 and size of each
        version (sidecar file, not the .sg1).
      - segment-log INDEX lines: plaintext size, SHA-256 and log-add path
        per entry, unless the log was created with --private-index
        (log=5: sealed with AES-256-GCM under an HKDF-derived per-entry
        key; see docs/SEGMENT-LOG.md "Private INDEX"); star= is keyed.
      - constellation card member names: hidden only when the card itself
        is encrypted; star counts and sizes are always visible.
    Without `--pad`: give encrypted outputs neutral names and do not rely
    on the size of an encrypted .sg1 being secret. With `--pad bucket` or
    `--pad max`, only the bucket / power-of-two size shows.
  Always visible: that the file is a .sg1, whether it is encrypted, its
    mode and shard counts, the ciphertext length (or its bucket once
    padding is used), and file-system names and dates.
  Rollback and replay: an older valid Sigil of the same file is
    indistinguishable from the current one without an external record
    (vaults and segment logs add one; see docs/SEGMENT-LOG.md).
  Destruction beyond the budget: more than n-k bad shards, or all copies.
    Keep a second copy; Sigil is not a backup schedule.
  Compromised endpoints, key theft, malware, side channels, coercion,
    traffic analysis, and the Covenant string (a label, never enforced).
